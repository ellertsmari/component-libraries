Component libraries

How do you eat an elephant? One piece at a time. These two pages show how real teams split big products into small components, and the programming ideas that make it work: abstraction, modularity, dependencies and decoupling. Each page puts two design systems side by side, so you see every idea answered in two different ways.

Start here · Iceland

Hanna and Ísland.is

Hanna · Reykjavík City Ísland.is · Digital Iceland

The design systems behind Reykjavík's websites and island.is. Both publish their components in Storybook, but Storybook hides the interesting part. This page follows one button all the way down: where the CSS comes from, where the imports point and how the colours are stored.

Why play with it

  • See one problem solved in opposite ways. Hanna's contract is CSS class names, Ísland.is's is React components.
  • Change a colour token live, and feel the difference between a CSS variable and a value baked in when the app is built.
  • Do a five-minute exercise with nothing but a browser, then rebuild the Ísland.is setup in Vite and see every hidden layer from the inside.
  • Get to know the code behind Icelandic public websites, the kind you meet working for the city, the state or the agencies that build for them.

Then · The world

Carbon and Material UI

Carbon · IBM Material UI · Google's Material Design

IBM's design system, and the most used React library built on Google's Material Design, downloaded millions of times a week. The same ideas at a much bigger scale, with libraries you can install in your own project today.

Why play with it

  • Run the real Material UI library inside the page and watch it write CSS in your browser as you change the theme.
  • Switch Carbon between its four themes by changing one class, and see why tokens make dark mode easy.
  • Measure modularity yourself. The same page builds to 1.2 MB of CSS or 130 KB, depending on what you import.
  • Learn from real dependency problems: a Sass update that broke Carbon's build on the day we tested it, and a well-known library that was retired.

What you'll practise

The same ideas, on both pages

The problems a component library solves

  • Dividing the work between the people in a group
  • Knowing where to start on a big project
  • One piece at a time instead of one huge project
  • Consistency, and changing something in one place

The programming ideas underneath

  • Abstraction: hiding the details behind a simple surface
  • Modularity: separate parts you take only when you need them
  • Dependencies: what each part needs, and what breaks
  • Decoupling: changing one part without breaking the rest

Both pages end with why this matters more now that AI writes so much code: an AI assistant gives you generic components, and knowing your own product is what turns them into the right ones.
